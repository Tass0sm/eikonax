#+title: eikonax

JAX-based numerical solvers for eikonal and Hamilton-Jacobi-Bellman (HJB)
equations on regular grids. An eikonal equation |grad u|_G = 1 (arrival-time
field for a given, possibly anisotropic, Riemannian metric G) is the
stationary, shortest-time special case of an HJB equation -- both are
solved here the same way: value iteration over a discretized set of
candidate moves (a semi-Lagrangian scheme), which is simple to get right
for a genuinely anisotropic metric (no local finite-difference stencil to
derive per equation) and vectorizes cleanly on GPU via JAX.

* Setup

#+begin_src sh
poetry install
#+end_src

* ~eikonax.fsm~: general N-dimensional Fast Sweeping Method

The core solver, dimension- and manifold-agnostic. Given:

  - a grid shape, per-axis physical resolution, and per-axis periodicity
    (so e.g. an angular axis can wrap while a translation axis doesn't),
  - a Riemannian metric matrix ~G~ at every grid node (`(*grid_shape, n,
    n)`, symmetric positive definite),
  - a JAX-jittable speed field ~speed_fn(coords) -> speed~ (obstacles are
    just ~speed_fn(x) ~ 0~ there; anything in between is slow terrain, a
    soft margin, whatever the caller wants),

~fsm.Solver~ computes the arrival-time field from one source state to
every other grid state.

** Candidate moves

Every integer grid-offset vector within a max ~radius~ of the origin, on
every axis, excluding the zero vector -- e.g. for a 3-D grid, ~radius=2~
gives all of ~{-2,...,2}^3 \ {0}~, 124 directions. Every such offset lands
EXACTLY on a grid-neighbor node (no interpolation needed anywhere), and --
this is the actual point of using a wide, N-D stencil instead of two
separate "translate" and "rotate" move families (an earlier version of
this package's SE(2) solver) -- an offset can be nonzero in MULTIPLE axes
at once, e.g. simultaneously translating AND rotating in a single
candidate move. A scheme that only ever offers axis-separated moves cannot
represent that at all, which is why it could never produce a shortest path
that actually turns into its direction of travel: any use of rotation
always paid its full cost immediately, with no way to blend it into
forward progress (confirmed directly, see ~tests/test_se2.py~'s
combined-moves test). Larger ~radius~ gives finer angular resolution at
the cost of ~(2*radius+1)^n~ candidates -- exponential in dimension, so
keep it modest beyond 2-3 axes.

The cost of taking offset ~o~ from node ~X~ is the metric length of the
physical displacement, divided by the WORSE (lower) of the speeds at every
lattice point the move passes through (not just its two endpoints -- a
wide-radius move can otherwise tunnel straight through a thin,
sub-radius obstacle without ever landing on it; a real bug this package's
own tests caught, fixed via ~fsm._segment_lattice_points~, a Bresenham-
style line rasterization of each offset). A move touching a zero-speed
node anywhere costs ~inf~, which naturally keeps the value iteration from
ever finding a cheap path through an obstacle -- no separate masking/
pinning step needed; ~inf~/~nan~ are clipped back to a finite sentinel
after every sweep so the returned field stays well-behaved for anything
downstream that interpolates it.

** The numerical method

Value iteration (Bellman fixed-point / semi-Lagrangian fast sweeping):
every grid node's arrival time is repeatedly updated (Jacobi-style, using
the previous full-grid iterate) as the minimum, over every candidate
offset, of "move cost + value at the offset target". Non-periodic axes
clamp at the boundary (Neumann-like); periodic axes wrap. Iterated to
convergence (or a fixed iteration budget) via a plain Python loop around a
JIT-compiled single-sweep step.

** Usage

#+begin_src python
import jax.numpy as jnp
import numpy as np
from eikonax.fsm import Solver

grid_shape = (64, 64)
metric = np.tile(np.eye(2), (*grid_shape, 1, 1))  # isotropic

def speed_fn(coords):
    x, y = coords[..., 0], coords[..., 1]
    return jnp.where((x > 3.0) & (x < 3.2), 0.0, 1.0)  # a thin wall

solver = Solver(grid_shape, resolutions=(0.1, 0.1), periodic=(False, False),
                 metric=metric, speed_fn=speed_fn, radius=3)
field = solver.solve(source=(32, 5))
#+end_src

~Solver.solve(source)~ is single-source, by design (mirrors the
~skfmm.travel_time~ single-source contract) -- a caller wanting an
all-pairs field builds ONE ~Solver~ (compiling its sweep once) and loops
over source states, disk-caching the result themselves (as
~po_goc_mpc.experiments.objectives.fmm.build_all_pairs_fmm_field~ already
does for its own single-source ~skfmm~ solves, and ~po_goc_mpc.
experiments.objectives.aniso_fmm~ does for this package's SE(2)
application).

* ~eikonax.se2~: anisotropic eikonal equation on R^2 x S^1

A thin SE(2)-specific application of ~fsm.py~: builds the grid/
periodicity/metric-field plumbing ~fsm.Solver~ needs for a "unicycle-ish"
~(x, y, theta)~ state space, over a `(ny, nx, n_theta)` grid (`x`/`y`
non-periodic, `theta` periodic).

** The default metric

~default_metric_at_theta(thetas, xi_lateral, xi_turn)~ builds the standard
"soft preference for moving/turning toward the current heading" model:
resolving `(dy, dx)` into the robot's own forward/lateral frame at heading
`theta` as `(u1, u2)`, and `dtheta` as `u3`,

#+begin_src text
F(theta, dy, dx, dtheta)^2 = u1^2 + u2^2/xi_lateral^2 + dtheta^2/xi_turn^2
#+end_src

moving along the current heading is unit cost, moving laterally costs
`1/xi_lateral`, turning costs `1/xi_turn` -- a SEPARATE ratio from lateral
translation, both in `(0, 1]`. This is a *soft* preference (nothing is
ever infinitely slow or forbidden), unlike a curvature-bounded Dubins/
Reeds-Shepp model -- the right choice for an omnidirectional legged robot
that CAN strafe or turn in place, just prefers not to.

*** Why ~xi_lateral~/~xi_turn~ are decoupled, not one shared ratio

A 90 degree reorientation costs about as much as (or more than) just
strafing the equivalent lateral distance under one shared ratio -- turning
needs it TWICE if the path has to turn back afterward -- so a shortest
path tends to strafe with a near-frozen heading rather than actually turn
to face its direction of travel, even at a fairly aggressive shared ratio.
Decoupling lets pure rotation be made cheap (`xi_turn` close to 1)
independently of how expensive strafing stays (`xi_lateral` small).

** ANY metric matrix can be substituted

~build_solver~'s ~metric_at_theta~ argument accepts a fully custom
`(n_theta, 3, 3)` array instead of the default diagonal one -- including a
metric with genuine translation-rotation COUPLING, which the earlier
version of this package (separate "translate" and "rotate" candidate move
families, no metric matrix at all) could not express no matter how its
scalar cost ratios were tuned: no shared-heading query ever benefited from
turning, since any rotation always paid its full "there and back" cost on
top of whatever a diagonal zig-zag could already achieve at no heading
cost. `fsm.py`'s combined-offset candidates remove that structural floor
(confirmed directly in `tests/test_se2.py`); the metric matrix here just
decides how strongly a turning preference is expressed once it's actually
representable.

** Usage

#+begin_src python
import jax.numpy as jnp
from eikonax.se2 import build_solver

def free_speed_fn(coords):
    return jnp.ones(coords.shape[:-1])

solver, thetas = build_solver(
    ny=64, nx=64, resolution=0.1, n_theta=16, speed_fn=free_speed_fn,
    xi_lateral=0.4, xi_turn=0.9, radius=2,
)
field = solver.solve(source=(32, 32, 0))
# field.shape == (64, 64, 16); field[i, j, k] = arrival time from the
# source state to (x[j], y[i], theta[k]).
#+end_src

~mask_speed_fn(mask, resolution)~ bridges a binary occupancy mask (e.g.
from a pyrobosim ~OccupancyGrid~) into the ~speed_fn~ `fsm.Solver` wants,
for the common case of a plain binary obstacle layout.

* ~eikonax.strategies~: one ~solve(domain, ...)~ per method, kwargs -> CLI

Both solvers are exposed as a strategy: a module with a
~solve(domain, *, <configuration keyword arguments>, progress_fn=None)~
function whose keyword arguments *are* its configuration. Both take their
environmental constraints the same way -- a ~domain~ object
(~eikonax.domains~) carrying the geometry, periodicity, speed field and
metric.

  - ~strategies.fsm.solve~ -- the grid Fast Sweeping sweep (exact, one
    solve per source; ~all_pairs=True~ runs the per-source loop).
  - ~strategies.ntfields.solve~ -- physics-informed training of a
    continuous all-pairs neural field; ~objective="td_ntfields"~ selects
    the implementation (see below).

~eikonax.scripts.solve~ builds its CLI by introspecting those signatures
(~eikonax.config~, ported from ~dynamic-hierarchy~'s ~config_utils.py~), so
every knob is a flag and ~--strategy ntfields --help~ / ~--strategy fsm
--help~ show different options:

#+begin_src sh
python -m eikonax.scripts.solve --strategy fsm --domain se2 --scenario wall \
    --ny 41 --nx 41 --n-theta 16 --radius 3

python -m eikonax.scripts.solve --strategy ntfields --domain se2 --scenario free \
    --epochs 2000 --batch-size 1000
#+end_src

~--scenario~ picks a named obstacle layout (~eikonax.scenarios~: ~free~,
~wall~, ~gap~) since a ~speed_fn~ callable cannot be passed on a command
line; Python callers pass their own ~speed_fn~ to the domain constructor.

#+begin_src python
import jax.numpy as jnp
from eikonax.domains import se2_domain
from eikonax.strategies import fsm, ntfields

def free_speed_fn(coords):
    return jnp.ones(coords.shape[:-1])

domain = se2_domain(free_speed_fn, ny=64, nx=64, resolution=0.1, n_theta=16,
                    xi_lateral=0.4, xi_turn=0.9)

field = fsm.solve(domain, source=(32, 32, 0), radius=2)   # (64, 64, 16)
model = ntfields.solve(domain, epochs=2000)               # a trained Model
#+end_src

* ~eikonax.strategies.ntfields~: neural travel-time fields (TD-NTFields)

A learned, continuous, ALL-PAIRS alternative to the grid sweep.
~fsm.Solver.solve(source)~ sweeps one grid per source, so an all-pairs
field costs one sweep per source state (which is why the downstream
consumer caches them to disk). ~ntfields~ instead fits a single two-point
network ~T(x0, x1)~ to the same eikonal equation by physics-informed
training -- no grid, no per-source solve, and differentiable end to end,
at the price of being approximate.

It is a port of *TD-NTFields* (Ni, Pan & Qureshi, ICLR 2025) from the
~ntrl-demo~ reference implementation, generalized from "isotropic
Euclidean speed field" to "arbitrary per-point Riemannian metric plus
speed field" -- the same generalization ~fsm.py~ makes on the grid side,
so a ~Domain~ and an ~fsm.Solver~ can be handed the same
`(metric, speed_fn)` and compared node for node.

Three pieces, following the method/backend split of the ~srms~ project:

  - ~eikonax.domains~ -- the continuous counterpart of ~fsm.Solver~'s
    `(grid_shape, resolutions, periodic, metric, speed_fn)`: a box with
    per-axis periodicity, a speed field, and an INVERSE metric (`fsm`
    measures the length of a finite displacement and wants ~G~; the PDE
    measures the length of a covector `grad T` and wants ~G^-1~).
    ~se2_domain~ mirrors ~se2.build_solver~'s conventions exactly, down to
    the `(y, x, theta)` axis order, and ~domain.fsm_solver()~ hands the
    SAME domain to the grid side.
  - ~eikonax.backends~ -- the model design (`metric_net`).
  - ~eikonax.strategies.ntfields~'s ~objective=~ -- the training objective
    (`td_ntfields`, the only one so far).

** The backend: a learned quasimetric, not a regression head

`T(x0, x1)` is not read off an output neuron. Both endpoints go through
one shared, row-wise spectrally-normalized (~1-Lipschitz) encoder `f`, and
the travel time is a smooth-max distance between the two embeddings:

#+begin_src text
d = sqrt((f(x0) - f(x1))^2 + eps)          per feature
T = out_scale * sum_g smoothmax_g(d)       log-sum-exp max over each group of features
#+end_src

so `T` is symmetric, non-negative, and minimal on the diagonal *by
construction*: the boundary condition holds for free, for every source, and
the triangle inequality is approximately structural rather than trained.
This is what makes the Bellman (TD) loss below well posed, and it is why
this port keeps the two-point form rather than the fixed-source
`T = base/tau` factorization that the ~srms~ project's own NTFields ports
use.

The input is a random-Fourier feature map with a FROZEN matrix `B`. On a
periodic axis `B`'s row is rounded to integers -- normalized periodic axes
have period exactly 1 -- so the network is exactly periodic in `theta` by
construction, not by training.

** The objective

Writing `|p|_x = sqrt(p^T G(x)^-1 p)` for the dual norm of a covector, the
eikonal equation is `S(x) * |grad T|_x = 1`, and

#+begin_src text
L = mean[ (w_E*L_E + w_TD*L_TD + w_N*L_N) * exp(-lambda_C * T) ]
#+end_src

with every term evaluated at BOTH endpoints of every pair:

  - `L_E  = (sqrt(S(x) * |grad_x T|_x) - 1)^2` -- the eikonal residual.
  - `L_TD = (T - stopgrad[T(x - dx, x') + dt])^2` -- a Bellman backup one
    characteristic step `dx = td_step * S(x) * G(x)^-1 grad_x T` toward the
    other endpoint, charged at the ground-truth `dt = td_step / S(x)`, and
    masked wherever `T < dt` (stepping would overshoot past the target).
    This finite-scale term is what "TD" names, and it is what carries
    information further than the infinitesimal `L_E` can.
  - `L_N  = (1.001 - S(x)) * |S(x) grad_x T + n(x)|_x^2` -- near an
    obstacle the characteristic must run along the obstacle normal
    `n = grad S / |grad S|_x` rather than through it. (The reference reads
    `n` from a precomputed surface-normal dataset; taking it from the speed
    field's own gradient is what makes this work for any `speed_fn`, and it
    degenerates harmlessly to a weak regularizer for a hard binary mask,
    whose gradient is zero.)
  - `exp(-lambda_C * T)` is the causality curriculum: near pairs are fit
    first, far pairs only once the near ones are cheap.

Pairs are drawn the way the reference draws them -- `x1 = x0 + unit *
U(0, pair_radius)`, so short-range pairs are common. Drawing both endpoints
independently instead concentrates every pair near the domain diameter,
where the curriculum weight is uniformly tiny and the field never gets
anchored; this is not a detail.

** Weak supervision: a PRM anchor (~roadmap_weight~)

The curriculum's cost is that far pairs -- and pairs separated by an
obstacle -- get almost no signal until the near field converges, and the
local residual only carries information one ~td_step~ at a time. ~srms~'s
~weak_supervision.py~ fixes the analogous single-source problem by
factoring ~T = base · exp(g)~ over an RRT* tree; that doesn't transfer
(fixed quasimetric backend, all-pairs field). A *probabilistic roadmap*
does: ~ntfields.roadmap.build_roadmap~ samples free nodes once, connects
each to its ~k~ nearest by a collision-checked, slowness-weighted edge, and
runs all-pairs shortest paths, giving an obstacle-aware approximate
geodesic ~d_PRM(x0, x1)~ for *any* pair. With ~roadmap_weight > 0~,

#+begin_src text
L += roadmap_weight · mean_valid[ (T − stopgrad d_PRM)² ] / mean_valid[ d_PRM² ]
#+end_src

is added (masked to pairs the graph connects). It is deliberately *outside*
the ~exp(-lambda_C · T)~ curriculum -- its whole job is to anchor the far /
around-obstacle pairs the curriculum suppresses. ~roadmap_weight = 0~ (the
default) builds nothing and is byte-for-byte the plain objective.

#+begin_src python
model = ntfields.solve(domain, epochs=2000, roadmap_weight=1e-2,
                       roadmap_nodes=256, roadmap_k=10)
#+end_src

** Usage

#+begin_src python
import jax.numpy as jnp
from eikonax.domains import se2_domain
from eikonax.strategies import ntfields

def free_speed_fn(coords):
    return jnp.ones(coords.shape[:-1])

domain = se2_domain(free_speed_fn, ny=64, nx=64, resolution=0.1, n_theta=16,
                    xi_lateral=0.4, xi_turn=0.9)
model = ntfields.solve(domain, epochs=2000)   # objective="td_ntfields" by default

model.time(X0, X1)                       # arrival time between physical coordinates
model.gradient(X0, X1)                   # dT/dx0, dT/dx1 -- descend -dT/dx1 to plan
field = model.field((3.2, 3.2, 0.0), (64, 64, 16))   # same shape se2.solve returns
#+end_src

Any custom metric is accepted the same way ~se2.build_solver~ accepts one:
pass ~metric_inv_fn~ to ~se2_domain~, or build a ~BoxDomain~ directly for a
non-SE(2) state space.

** Caveats

  - `td_step` is a length in the domain's own METRIC units. The reference's
    0.03 is ~3% of its unit-span, identity-metric box; scale it with your
    domain.
  - ~ntfields.solve~'s keyword defaults are the reference implementation's,
    including its training loop: an epoch whose loss grew by more than
    ~rollback_ratio~ is discarded and re-run from a randomly chosen recent
    checkpoint. That rollback is what lets the objective's `sqrt` and `1/S`
    terms train at a fixed learning rate.
  - This is an approximation, and unlike ~fsm~ it has no monotone
    convergence guarantee. Score it against ~fsm.Solver~ on the same
    `(metric, speed_fn)` before trusting it downstream. Two measurements
    on CPU, both well under the reference's 5000x5x2000 budget: a free
    2-D unit box (1200 epochs x 4 x 1000) reaches 1.3% relative L2 error
    against exact Euclidean distance with a mean predicted speed of 0.998;
    a 21x21x8 SE(2) grid with a wall (1500 epochs x 4 x 1000, scored
    against the ~fsm~ sweep) reaches 15.8% mean relative error at
    correlation 0.89, with the error concentrated in the expensive tail
    (predicted max 18.0 against a true 27.3) -- exactly where the
    `exp(-lambda_C * T)` curriculum gets to last.
